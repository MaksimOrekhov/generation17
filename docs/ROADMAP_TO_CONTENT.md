# ROADMAP TO CONTENT — что сделать до массового наполнения

> **Статус:** предложение по итогам [Core Systems Audit](CORE_SYSTEMS_AUDIT.md), **не утверждённый план**. Ни один этап не начат. Решение о каждом этапе принимает владелец проекта.
> **База:** `main` = `74fe07d` (T9 «Личное время» уже в `main`), 29.10.2026.
> **Сложность:** S — до дня работы исполнителя, M — несколько дней, L — около недели, XL — больше.

## 0. Коротко

Фундамент жизни (время, ритм, экономика, сохранения, проверки) готов и надёжен. До сотен событий не хватает **не новых симуляций, а выразительности**: контент не может сослаться на конкретное прошлое решение, поменять вариант ответа или фразу по прошлому, прочитать связь или смерть человека, открыть новую линию без TypeScript. Люди — семь фиксированных ролей, а партнёр героя — всегда друг детства. Директор надёжно доставляет продолжения, но при большой библиотеке размывает начала линий, а выбор стратегии игрока почти не меняет набор историй.

**Обязательных этапов четыре** (P0): язык контента, люди как данные, контроль качества контента, директор для большой библиотеки. **Желательных — три** (P1), и их можно делать параллельно с первыми пакетами: жизнь вокруг героя, финальная хроника и объяснимость, занятия. Остальное — после первых пакетов или после большого плейтеста.

```text
           ┌──────────────────────┐
           │ 1. Язык контента v2   │──────────────┬───────────────┐
           │    + журнал решений   │              │               │
           └──────────┬───────────┘              │               │
                      │                          ▼               ▼
 ┌──────────────────┐ │   ┌──────────────────┐  ┌───────────────┐ ┌─────────────┐
 │ 3. Контроль       │ │   │ 2. Люди как      │  │ 4. Директор    │ │ 6. Хроника и │
 │    качества (с 0) │◄┘   │    данные        │  │    для большой │ │ объяснимость │
 └────────┬─────────┘     └────────┬─────────┘  │    библиотеки  │ │   (P1)      │
          │                        │            └──────┬────────┘ └─────────────┘
          │                        ▼                   │
          │               ┌──────────────────┐         │   ┌──────────────┐
          │               │ 5. Жизнь вокруг   │         │   │ 7. Занятия    │
          │               │    героя (P1)     │         │   │   (P1)       │
          │               └──────────────────┘         │   └──────────────┘
```

**Параллельно, без конфликтов файлов:** этап 3 (кроме проверок новых полей) можно начинать сразу, одновременно с этапом 1. Этап 2 начинается после того, как в этапе 1 зафиксирован формат условий и эффектов (первые 1–2 дня этапа 1). Этапы 4 и 6 после этапа 1 идут параллельно (директор / UI и хроника — разные файлы). Этапы 5 и 7 — после 2 и 1 соответственно, тоже параллельно.

## 1. Обязательные технические задачи (P0)

### Этап 1. Язык контента v2 и журнал решений — **P0, L**

**Игровая ценность.** Прошлое героя становится видимым в каждой сцене: тот же сюжет звучит иначе для того, кто когда-то заступился за друга; вариант «позвать сестру» появляется только если сестра есть и вы не в ссоре; линия о ремесле живёт в JSON и видна в «Развилках».

**Конкретная проблема** (аудит §3.D, §5):
- у варианта ответа нет условия показа (`ChoiceDef`, `src/domain/types.ts`), тексты `body`/`result` статичны — меняются только имена и формы рода. Каждое «по-разному для разного прошлого» сейчас = копия сюжета (`family-need-cell-small/medium/large`);
- `requires` — только «И»; нет «ИЛИ», нет условий «видел сюжет X», «выбрал Y», связи с человеком, смерти человека, навыков, показателей корабля (`src/content/types.ts`, `src/content/load.ts`);
- новую линию `arc` и новую категорию в JSON создать нельзя: валидатор берёт их только из кода (`collectKnown(codeStorylets, …)` в `scripts/content.ts`; проверено пробой — «линия из списка …»);
- тон сюжета для директора задаётся таблицей в коде по `id` (`TONE_OVERRIDES`, `director.ts`); у JSON — только по категории;
- нет записи «какой вариант выбран в каком сюжете»: только флаги, которые придумывает автор, и `forks` для восьми кодовых линий. Индекс варианта как ссылка хрупок.

**Что уже реализовано.** Компиляция JSON (`compileRequires`, `compileStorylet`), 24 вида условий (флаги, окна `since/until`, люди, работа, деньги, жильё, покупки, услуги), эффекты (показатели, навыки, связи, флаги, деньги, покупка, переезд, ребёнок), формы рода, приоритеты `followup/critical`, окна `expiresIn`, строгий валидатор формы.

**Что добавить.**
1. `choices[].id` — стабильный ключ варианта (необязателен для старого контента; для новых пакетов обязателен).
2. `choices[].requires` — вариант показывается, только если условие выполнено (минимум один вариант всегда доступен — проверка валидатора и движка).
3. `variants` для `body`, `result` и `text` момента: список `{ requires, text }`, первый подходящий заменяет базовый текст. Без RNG.
4. Новые условия: `any: Requires[]` (ИЛИ), `seen` / `notSeen` (сюжеты), `chose: { "<storylet>": ["<choice-id>"] }` с необязательным окном лет, `bond: { "<person>": { min, max } }`, `dead: [...]` / `absent: [...]`, `skill`, `ship`, `birthWealth`, `trait`.
5. Поля сюжета: `tone`, `tags` (темы для директора), `group` (взаимоисключающие ситуации: «одна первая любовь за жизнь») и объявление линий/категорий в JSON (`content/lines.json` или манифест пакета).
6. `choices[].epilogue` — необязательная строка прошедшего времени для финальной хроники (этап 6); вводится сейчас, чтобы не возвращаться к сотням вариантов.
7. `GameState.decisions: { id, choice, age }[]` — журнал решений (≈ 25 записей за жизнь, < 2 КБ). Миграция старых сохранений: пустой журнал с пометкой, `seen` остаётся источником для `seen`.
8. Единый список людей для меток в движке и валидаторе (сейчас `sibling` в `body` проходит валидатор, но не охраняется фильтром `tick()`, и герою без брата/сестры текст подставит «брат или сестра»); метка `{{parent2}}` (отец сейчас не называется по имени нигде).

**Зависимости.** Нет. Блокирует этапы 2, 4, 6, 7 и все пакеты.

**Минимальный прототип.** Расширить компилятор и валидатор, затем перенести одну кодовую линию целиком в JSON — «Сосед» (8 сюжетов, `storyletsLines.ts`) — и доказать эквивалентность. Плюс один сюжет с тремя вариантами текста вместо трёх копий.

**Критерий успешности.**
- Перенесённая линия эквивалентна кодовой **на одних и тех же состояниях**: для всех состояний, снятых из 200 жизней × 4 стратегии, совпадают доступность, окно, тексты и результат каждого варианта (флаги, показатели, память). Целые жизни сравнивать нельзя: место сюжета в каталоге меняет порядок взвешенного выбора, и RNG расходится законно.
- Любая из восьми кодовых линий выразима в JSON (проверка на бумаге, без обязательного переноса).
- Валидатор ловит: несуществующий сюжет/вариант в `chose`, вариант без доступного ответа, метку человека без гарантии.
- Все 874 теста проходят; сохранения T9 загружаются.

**Риски для существующих историй.** Условия чистые (без RNG) — порядок случайных чисел не меняется. Главный риск — скрытые варианты меняют индекс ответа у ботов аудитов: ссылаться на вариант по `id`, а боты T8/T9 переводить на `id`. Сохранения: `decisions` необязательно.

**Исполнитель.** Claude Opus.

### Этап 2. Люди как данные — **P0, M–L**

**Игровая ценность.** Партнёр, который не обязан быть другом детства; брат, который уехал в другой сектор; ребёнок-подросток со своим упрямством; наставник, ушедший на покой. Сцены знают, где человек и что между вами было.

**Конкретная проблема** (аудит §3.B):
- семь фиксированных ролей (`rollBirth`, `birth.ts`), у человека только `bond`, `age`, `alive`, `since`. Ни профессии, ни места, ни отношения к герою кроме числа;
- партнёр — это всегда `friend`: совместная жизнь проверяется по `friend` (`cohabitationOk`, `invariants.ts`), ветка «Любовь» целиком на друге детства;
- состояние отношений хранится глобальными флагами разных форматов (`friendState`, `loveStage`, `neighborPath`, `familyChild`), их нельзя обобщить;
- ребёнок один, появляется в 3,5% жизней ботов; детские сцены — до 14 лет, потом одна сцена после 65 героя; ребёнок не взрослеет в сюжетах;
- люди умирают только после 65 собственных лет и только случайно (`peopleTick`); никто не уезжает, не меняет работу, не заводит семью.

**Что уже реализовано.** Возраст и смерть людей, `since` (кто когда появился), `isKnown`, род и формы, `addPerson: child`, связь `bond` и её изменение, семейная поездка с участниками поимённо, инварианты присутствия.

**Что добавить.**
1. `Person.state: Record<string, string | number | boolean>` — состояние человека («где живёт», «работа», «в ссоре», «уехал»), записываемое эффектом `person: { "<id>": { … } }` и читаемое условием `person`.
2. Роли сверх рождения: `partner` (отдельный человек; миграция — существующая «Любовь» помечает друга как партнёра, а не создаёт нового), `child2`, `colleague`; общий `addPerson` с ролью и правилами имени.
3. Стадии ребёнка как данные: 0–6 / 7–14 / 15–25 / взрослый; выход из дома и собственная семья — состояния, не новые механики.
4. Метки и формы рода для всех ролей; условие «человек ушёл/уехал» отдельно от «умер».

**Зависимости.** Этап 1 (формат условий и эффектов).

**Минимальный прототип.** `partner` + `Person.state` + три стадии ребёнка; перевести «Любовь» на `partner` с совместимостью сохранений; написать 4–6 сюжетов-проб (не пакет): партнёр — не друг детства; взрослый ребёнок уезжает в другой сектор.

**Критерий успешности.** Старые сохранения с `livingTogether` загружаются без потери; инварианты (`findInconsistencies`) обобщены на роли; тесты «упоминается только живой и известный» проходят для всех ролей; на 600 жизнях доля героев с партнёром/ребёнком определяется контентом и выбором, а не единственной цепочкой из двух случайных событий.

**Риски.** Самый рискованный этап для сохранений и линий «Любовь»/«Дружба». Делать после этапа 1, одним исполнителем, с тестами миграции.

**Исполнитель.** Claude Opus.

### Этап 3. Контроль качества контента — **P0, M**

**Игровая ценность.** Опосредованная: сотни событий от двух исполнителей не ломают друг друга, обещанные продолжения приходят, тексты не повторяются.

**Конкретная проблема** (аудит §5, §8):
- валидатор проверяет имя флага, но не значение: `flagIs: { friendState: "estrangd" }` проходит (проверено пробой);
- нет пространства имён: 128 разных флагов, 54 строковых, без описания и владельца; две команды могут записать один флаг по-разному;
- проверки повторяемости, доставки и мотивов существуют только как разовые скрипты аудитов (`audit`, `audit:economy`, `audit:time`) и новый `audit:variety`;
- нет отчёта связей «кто пишет флаг → кто читает».

**Что уже реализовано.** Валидатор формы и диапазонов, проверка «флаг где-то ставится», запрет меток без гарантии, проверка денежных сюжетов, `npm run audit` (частоты, ритм, поздняя жизнь), `npm run audit:variety` (этот аудит: повторяемость, доставка, мотивы, нагрузочный опыт).

**Что добавить.**
1. Манифест пакета (`content/packs/<id>/pack.json`): префикс ID, флаги со значениями и спутником `…Age`, `reads`, линии, группы ([CONTENT_SCALING_PLAN §1.1](CONTENT_SCALING_PLAN.md)).
2. Валидатор: значения флагов, префиксы ID, запись чужих флагов, `…Age` у флагов-окон, сюжеты без выхода (развилка без продолжений и без пометки «тихий исход»).
3. `npm run content:graph` — Markdown-отчёт связей.
4. `audit:variety`: режим сравнения двух прогонов (`--compare`), печать одной жизни по seed для литературного ревью, n-граммы и совпадающие концовки, отчёт по пакету.
5. Тест в `npm test`: каждое продолжение (`followup`/`critical`) доставлено ≥ 95% там, где было доступно, на фиксированной выборке (быстрая версия на 60 жизнях).

**Зависимости.** Пункты 1–3 и 5 не зависят от этапа 1 и могут начинаться сразу; проверка новых полей (`chose`, `variants`, `group`) — после этапа 1.

**Минимальный прототип.** Манифесты для двух существующих файлов (`economy-t7`, `family-01`) и проверка значений флагов.

**Критерий успешности.** Опечатка в значении, чужой флаг, ID без префикса — ошибки сборки; отчёт связей строится для всего каталога; сравнение до/после пакета — одной командой.

**Риски.** Почти нет: инструменты не меняют игру. Не превращать в редакторскую систему (§4 ниже).

**Исполнитель.** Codex (по спецификации) + ревью Claude Sonnet.

### Этап 4. Директор для большой библиотеки — **P0, M**

**Игровая ценность.** Каждая жизнь держит 2–4 живые линии, а не набор случайных одноразовых сцен; то, что игрок делает (фокус года, траты, выборы), меняет, о чём будут следующие истории.

**Конкретная проблема** (аудит §3.F, §6):
- **размывание начал линий.** В нагрузочном опыте (копии JSON-каталога до 1 121 сюжета) решений на жизнь столько же (≈ 26), продолжения доставляются (99,6–99,9%), но продолжений восьми кодовых линий на жизнь становится меньше: 4,6 → 1,6. Семена линий — обычные события, и при большом пуле они выпадают реже;
- **стратегия не меняет историю.** Разница частот сюжетов Family/Careerist — 0,021, ниже шумового порога 0,032 (аудит §4.2); у Family ребёнок так же редок, как у Careerist; фокус «Отношения» и «Отдых» не меняет сюжетов (RHYTHM_AUDIT §1.5);
- **группы ситуаций.** При сотнях вариантов одной ситуации ничто, кроме ручных `flagNot`, не мешает «трём первым любовям» в одной жизни;
- моменты повторяются внутри жизни: 45% предложенных — уже виденные.

**Что уже реализовано.** Интервалы, бюджет напряжения, приоритет продолжений, «последний шанс» и `dueByDeadline`, штраф повтора категории, бонус ×2,5 начатой линии (только кодовые линии), одна сцена в год, детерминизм; 0 потерянных продолжений в 1 200 жизнях.

**Что добавить.**
1. **Бюджет линий:** семена (`fork`/сюжеты, открывающие линию) получают вес от числа открытых линий героя: меньше двух — выше, больше четырёх — ниже.
2. **Темы и намерения:** `tags` сюжетов (этап 1) взвешиваются по фокусу года и по сделанному (покупки, работа, люди); без нового интерфейса.
3. **Группы:** `group` — не больше одного сюжета группы за жизнь или за окно лет.
4. **Свежесть моментов:** вес уже виденного в этой жизни момента снижается.
5. **Тон из JSON** (`tone`), таблица `TONE_OVERRIDES` остаётся для кода.

**Зависимости.** Этап 1 (`tags`, `group`, `tone`, линии в JSON).

**Минимальный прототип.** Пункты 1–3 на нагрузочном опыте `audit:variety --scale` (уже есть).

**Критерий успешности.** На ×10 и ×25: продолжений кодовых линий на жизнь не меньше, чем на ×1 (≈ 4,6); доставка продолжений ≥ 99%; решений на жизнь 24–28; максимальный промежуток ≤ 6 лет. Различие стратегий: разница частот сюжетов Family/Careerist заметно выше шумового порога (сейчас 0,021 при пороге 0,032; цель уточнить после прототипа). Повторы моментов внутри жизни ниже 30%.

**Риски.** Меняет порядок RNG и, значит, все эталонные жизни (T6/T8/T9 baseline). Принять как ожидаемое изменение контента, обновить эталоны отдельным коммитом. Не переписывать директор целиком: это дополнительные множители веса и одна новая проверка.

**Исполнитель.** Claude Opus.

## 2. Желательные улучшения (P1) — параллельно с первыми пакетами

### Этап 5. Жизнь вокруг героя — **P1, M–L**

**Ценность.** Мир живёт без героя: друг сам меняет работу (G17-005), ребёнок сам уезжает (G17-006), авария водоочистки на годы меняет быт сектора (G17-007), травма надолго меняет занятость (G17-016).

**Проблема.** Нет событий без решения героя, кроме ежегодного дрейфа корабля и случайной сводки раз в 7 лет (`worldTick`): корпус проседает с 89 до 67 за жизнь без последствий (аудит §3.C), авария закрывает услуги только на год. Статусы занятости `sick` и `between` есть в экономике (`economy.ts`), но ничто их не включает.

**Реализовано.** Флаг `shipIncidentAge`, `servicesOpen`, зарплата и пенсия при `sick`/`between`, смерть людей.

**Добавить.** Вид контента `happenings` (JSON): условие, вероятность в год, эффекты (люди, корабль, флаги, занятость с длительностью), строка хроники; без остановки времени. Отдельный поток случайности мира (`hash32(seed, 'world', год, id)`) — первые шаги G17-009, не меняющие RNG героя. Эффект `work: { kind, years }`.

**Зависимости.** Этапы 1 и 2. **Прототип.** Одна цепочка «ограничение воды» с двумя исходами и одна самостоятельная судьба друга. **Успех.** На 600 жизнях: изменения людей и корабля видны в хронике и читаются сюжетами; RNG героя не меняется для жизней, где не сработало ни одно фоновое событие. **Риски.** «Генератор несчастий» — бюджет тона общий с директором. **Исполнитель.** Claude Opus (механика) + Codex (цепочки).

### Этап 6. Финальная хроника и объяснимость — **P1, M**

**Ценность.** Финал рассказывает именно эту жизнь (G17-010); игрок видит, почему сцена случилась.

**Проблема.** Эпитафия — три общие фразы с числами (`epitaph`, `engine.ts`); «Развилки» показывают только восемь кодовых линий, продолжения из JSON (T7, семья) в них не видны; окно решения не говорит, с чем связана сцена.

**Реализовано.** `forks`, `memories`, хроника, финальное окно с ровесниками, отчёт тестера.

**Добавить.** Хроника из журнала решений, `epilogue`, людей (кто рядом, кто ушёл, кто уехал), работы и экономики: блоки «Люди рядом», «Дело», «Не доведено до конца», «Обычные годы». Пометка в окне решения: «связано с решением в 23 года» — выводится из `requires`. Линии JSON в «Развилках».

**Зависимости.** Этап 1 (журнал, `epilogue`, линии в JSON); этап 2 для блока о людях. **Прототип.** 25–40 фрагментов (как в карточке G17-010). **Успех.** Проверка правдивости: каждое утверждение финала выводится из состояния (тест); на 100 жизнях нет двух одинаковых финалов. **Исполнитель.** Claude Sonnet (UI, сборка) + Opus (тексты фрагментов).

### Этап 7. Занятия — **P1, M**

**Ценность.** Личное время получает долгий смысл: ремесло, музыка, сад, кружок, общественная работа, наставничество, забота о стариках, занятия в старости.

**Проблема.** 62% личного времени взрослых не тратится, у пенсионеров — 69% (аудит §4.6); T9 прямо называет причину: не хватает поводов. Моменты — однодневки, а увлечение как длящаяся вещь не выражается.

**Реализовано.** Годовой лимит личного времени по режиму работы, цены моментов и покупок, «свободный вечер», условия `regime`.

**Добавить.** Объявляемые в JSON занятия: начать / продолжать / бросить, годовая цена в личном времени (1 единица), годы практики; условие `pursuit: { id, years }`; не больше двух активных. **Никаких шкал мастерства и прокачки**: годы практики — единственное число, остальное — сюжеты.

**Зависимости.** Этап 1. **Прототип.** Два занятия (ремесло, общественная работа) с 3–4 сюжетами и моментами каждое. **Успех.** У пенсионеров и на 0,6 ставки неиспользованное время падает ниже 50% без снижения лимита; занятия не стали обязательной стратегией (T8-проверка доминирования). **Исполнитель.** Claude Sonnet (механика по спецификации) + авторы пакетов.

## 3. Массовое создание контента

Начинается после этапов 1–4 (P0). Этапы 5–7 идут параллельно; пакеты, которым они нужны, ждут свой этап.

| Волна | Пакеты | Нужны этапы | Зачем первой |
|---|---|---|---|
| 1 | Партнёр и семья; профессии (по 8–12 решений на профессию по стадиям карьеры) | 1–4 | Самые большие дыры: семья в 3,5% жизней, профессии почти не различают жизнь |
| 2 | Занятия; взросление ребёнка 7–25 | + 7, 5 | Смысл личного времени; ребёнок, который растёт |
| 3 | Корабль рядом (бытовые последствия, ограничения, общественные споры); долгая старость 80+ | + 5 | Мир с последствиями, старость не только о памяти |
| 4 | Детство 0–11 (семена для поздних откликов); редкие тайны | 1–4 | Растит возвращения через десятилетия |

Размер пакета: 15–30 сюжетов и 15–40 моментов, не больше трёх линий. После каждого пакета — `audit:variety` до/после ([CONTENT_SCALING_PLAN §5](CONTENT_SCALING_PLAN.md)).

**Первый большой плейтест** — после волны 1, по [PLAYTEST.md](PLAYTEST.md), с вопросом «чем вторая жизнь отличалась от первой».

## 4. После первого большого плейтеста

Делать только если плейтест покажет потребность:

- Режим «Что, если» и повтор с развилки (G17-009, UI): нужен журнал **всех** входов игрока, не только решений.
- Наследие между жизнями (G17-013).
- Анимированные пиксельные сцены для отдельных событий (G17-017): 2–3 прототипа, когда станет ясно, какие события запоминаются.
- Новые профессии, позиции каталога трат, сектора — как P2 по ходу контента.
- Более глубокая модель корабля (несколько связанных переменных), если фоновые цепочки этапа 5 окажутся недостаточными.

## 5. Чего лучше не делать

- **Универсальный журнал фактов** (G17-008 в полном виде, `Ledger` из исследования SIMULATION_EVOLUTION): журнал решений этапа 1 + состояние людей этапа 2 + существующие флаги с манифестом покрывают «кто помог, когда сменил профессию, с кем поссорился, какую возможность отверг». Отношения между двумя другими людьми без героя — одно поле `Person.state`. Полный журнал имеет смысл только для финала уровня «всё, что было», и его можно будет вывести позже.
- **«Круг» из 6–10 симулируемых NPC с мечтами и годовым шагом:** дорого, трудно сделать заметным игроку; фоновые события этапа 5 дают тот же эффект для 1–3 важных людей.
- **Шкалы мастерства увлечений**, «уровни» дружбы, ещё одна валюта.
- **Редактор сюжетов** — JSON, манифест и отчёты достаточны ([CONTENT_SCALING_PLAN §6.3](CONTENT_SCALING_PLAN.md)).
- **Экономическая модель корабля** и управление показателями — противоречит GDD §1.
