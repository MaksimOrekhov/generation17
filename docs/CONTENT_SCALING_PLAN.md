# CONTENT SCALING PLAN — как писать сотни событий и не получить сотню одинаковых

> **Статус:** предложение к обсуждению, не утверждённый процесс. Ничего из описанного ниже ещё не реализовано, кроме того, что прямо названо существующим.
> **Основа:** [`CORE_SYSTEMS_AUDIT.md`](CORE_SYSTEMS_AUDIT.md) (факты и цифры), [`ROADMAP_TO_CONTENT.md`](ROADMAP_TO_CONTENT.md) (технические этапы), [`content/README.md`](../content/README.md) и [`content/STYLE.md`](../content/STYLE.md) (формат и голос).
> **Масштаб 500–1500 событий** — исследовательский ориентир из задачи, не квота.

## 0. Главная арифметика

За жизнь игрок видит **≈ 25–26 решений** и **≈ 80 моментов** (из них около половины — повторы, см. аудит §4.3). Это не изменится от размера библиотеки: ритм задаёт директор (интервал ≥ 2 лет, одно решение в год), и нагрузочный опыт подтвердил, что решений на жизнь остаётся ≈ 26 и при 1 121 сюжете.

Значит:

1. **Каждое новое событие увидит малая доля жизней.** При 500 сюжетах обычное событие показывается примерно в каждой двенадцатой жизни, где оно доступно; при 1 100 — в каждой двадцать восьмой (аудит §6). Писать событие, которое увидят 2% игроков, имеет смысл, только если оно делает жизнь *другой*, а не просто занимает слот.
2. **Разнообразие между жизнями дешевле получать вариантами, чем новыми слотами.** Один сюжет с тремя вариантами текста по прошлому героя (после этапа 1 дорожной карты) даёт три разных опыта в тех же 26 слотах. Сто новых одноразовых событий снижают повтор, но и размывают линии (аудит §6: продолжений старых линий на жизнь 4,6 → 1,6).
3. **Слотов на продолжения мало, и это лучшие слоты.** Продолжение доставляется в 99,7% случаев, но каждое занимает место. Пакет, который открывает больше линий, чем закрывает, вытесняет чужие обычные события. Поэтому у каждого пакета есть бюджет линий (§3.3).

Отсюда правило всего плана: **меньше, но связаннее**. Пакет из 25 событий, где 15 реагируют на прошлое, лучше пакета из 60 независимых сцен.

## 1. Тематические пакеты

### 1.1. Что такое пакет

Пакет — папка (или пара файлов) с одним манифестом и единым префиксом ID:

```
content/packs/<pack-id>/
  pack.json        манифест: id, префикс, автор/исполнитель, флаги, линии, группы ситуаций, возраст
  storylets.json
  moments.json
  happenings.json  (после этапа 5: события без решения героя)
```

Манифест — единственное новое «учётное» средство. Отдельный редактор или база сюжетов **не нужны**: JSON + валидатор + отчёты покрывают всё, что нужно двум исполнителям и владельцу. Технически манифест вводится этапом 3 дорожной карты; до него пакеты можно складывать по-старому, в `content/storylets/<pack>.json`, но с префиксом ID и списком флагов в шапке PR.

Минимальный манифест:

```json
{
  "id": "craft",
  "prefix": "craft-",
  "owner": "claude",
  "ages": [14, 90],
  "themes": ["увлечение", "руки", "наставничество"],
  "lines": [{ "id": "craft-carving", "title": "Резьба по пластику" }],
  "groups": ["first-craft"],
  "flags": {
    "craftCarving": { "values": ["started", "dropped", "taught"], "age": "craftCarvingAge" }
  },
  "reads": ["friendState", "familyChild"]
}
```

`flags` — то, что пакет **пишет** (только он); `reads` — чужие флаги, которые он **читает**. Валидатор (этап 3) отклоняет запись чужого флага и чтение значения, которое никто не пишет.

### 1.2. Оси деления

Пакет описывается одной главной осью и несколькими пересечениями. Главных осей пять:

| Ось | Примеры пакетов | Чем опасна |
|---|---|---|
| Возраст | раннее детство 0–5, школа 6–12, юность 13–19, молодость 20–29, зрелость 30–54, перелом 55–64, старость 65–80, долгая старость 80+ | Повтор структуры «сцена возраста» без связи с прошлым |
| Люди | мать и отец, брат/сестра, друг детства, партнёр, ребёнок 0–6 / 7–14 / 15–25 / взрослый, сосед, наставник, коллеги | Требует модели людей (этап 2), иначе всё через `friend` |
| Профессия | техник, медик, агроном, координатор; по стадиям: стажёр, мастер, старший, уходящий | Профессии почти не различают жизнь сейчас (аудит §3.A) |
| Занятия | ремесло, музыка, сад, архив, спорт в секторе, общественная работа, наставничество, забота о стариках | Без механики занятий (этап 7) — только моменты-однодневки |
| Корабль | быт сектора, ограничения воды, авария, переезд сектора, праздники, совет, поколенческий спор | Без «жизни вокруг» (этап 5) — только три сюжета на пороги показателей |

Пересечения задают **варианты**, а не новые пакеты: «юность × нижняя палуба», «зрелость × медик × ребёнок-подросток». Вариант — это `variants` в тексте или `requires` у выбора одного сюжета (этап 1), а не копия сюжета.

### 1.3. Порядок пакетов

Предлагаемая очередь по ценности на слот (подробно — в дорожной карте §3):

1. **Люди рядом: партнёр и семья** — сейчас ребёнок появляется в 3,5% жизней, совместная жизнь — в 0,8% (аудит §4.2). Это самая большая дыра в «спокойной содержательной жизни».
2. **Профессиональные траектории** — по 8–12 решений на профессию по стадиям карьеры; связываются с T5 (разряды, переобучение) и с занятостью.
3. **Занятия и личное время** — дают 62% неиспользованного времени смысл.
4. **Взросление ребёнка и взрослые дети.**
5. **Корабль рядом** — бытовые последствия аварий, сезонные ограничения, общественные споры.
6. **Детство 0–11** — сейчас 3 + 8 сюжетов; важнее не количество, а «семена» для поздних откликов.
7. **Долгая старость 80+** — потери, забота, прощания (сейчас только воспоминания и архив).

## 2. Литературное качество

### 2.1. Что уже работает

Лучшие образцы проекта — цепочки T7 («Ячейка в архиве», «Дверь, которая закрывается», «Чужая версия той недели», [`docs/audit/narrative-t7.md`](audit/narrative-t7.md)). В них есть то, что нужно масштабировать: просьба без просьбы, поведение вместо объяснения, четыре ответа как четыре правды, отклик через годы, который **приносит новую информацию**, а не повторяет выбор.

### 2.2. Правила для пакетов (дополнение к STYLE.md)

1. **У каждого человека в пакете есть собственное желание**, не совпадающее с желанием героя. Мать хочет не общения, а одиночества; сестра платит за ячейку, чтобы не решать. Если NPC хочет того же, что герой, сцена плоская.
2. **Один сюжет — одна неожиданная деталь мира корабля** (переработка вещей, очередь на дверь, «бессрочная» бирка). Мир должен объяснять, почему эта ситуация невозможна на Земле.
3. **Ответы — характеры, не степени.** Запрещён шаблон «активно / осторожно / ничего не делать с −1 стресса». Проверяется на ревью.
4. **Платный, смелый и «добрый» ответы не должны быть правильными.** Через годы каждый получает свою цену и свою тихую радость.
5. **Отклик сообщает новое.** Плохой отклик: «Ты вспоминаешь тот день». Хороший: «Ты не узнаёшь ни одной детали её рассказа».
6. **Диалог короткий и неполный.** Реплика — одна-две фразы; люди недоговаривают, перебивают, говорят о другом.
7. **Обычная жизнь — полноценная тема.** В каждом пакете не меньше трети сюжетов без кризиса (тон `calm`/`warm`), но со ставкой: выбор говорит, кем становится герой.
8. **Не больше одной «смерти/потери» на пакет**, если пакет не о потерях. Директор следит за напряжением, но смысловая усталость им не измеряется.

### 2.3. Ревью

Каждый пакет проходит два чтения:

- **автоматическое** — валидатор, отчёт мотивов, достижимость (§5);
- **литературное** — другой исполнитель (Claude ↔ Codex) или владелец читает пакет целиком *как жизнь*: по одной симулированной биографии на каждый вариант главной развилки. Сегодня такую биографию даёт отчёт тестера в игре (`buildReport`, `src/ui/report.ts`); печать жизни по seed и стратегии из командной строки — часть этапа 3. Вопросы ревью: где герой ведёт себя не так, как раньше; где человек говорит не своим голосом; где сцена повторяет другую по форме; какой отклик ничего не сообщает.

Результат ревью — короткий список в PR, а не переписанный пакет.

## 3. Продолжения через десятилетия

### 3.1. Три горизонта

| Горизонт | Через сколько | Что делает | Механика сейчас |
|---|---|---|---|
| Эхо | 1–5 лет | Момент или короткий сюжет показывает цену выбора | момент с `requires.flagIs` + `ownedYears`/`since` |
| Поворот | 5–15 лет | Новое решение, состав вариантов зависит от первого | `priority: followup`, окно `since`/`until`; после этапа 1 — `requires` у вариантов |
| Возвращение | 15–40 лет | Поздняя сцена о прошлом, часто в старости | `since ≥ 15`; после этапа 1 — `chose` по журналу решений |

Хорошая линия имеет **одно семя, два-три поворота и одно возвращение**, причём ветки расходятся по содержанию сцен, а не по ±числам (GDD §7).

### 3.2. Как писать, чтобы продолжение пришло

- Окно продолжения — не уже 5 лет и не позже `max − 3` (иначе ритм «последнего шанса» сдвигает его в год сразу после другого решения).
- У каждой ветки семени есть хотя бы одно продолжение или осознанная пометка «тихий исход» в манифесте. Отложенное решение (`deferred`, `waiting`) всегда закрывается (существующее правило README).
- Продолжение проверяет, что человек жив и известен (`present`), и **проверяет не только флаг, но и состояние сейчас**: каюта ещё твоя, человек не уехал, связь не разорвана.
- После этапа 1: продолжение ссылается на решение по `chose` (журнал решений), а не на флаг, если флаг нужен только для этого. Так пакеты не плодят флагов.

### 3.3. Бюджет линий пакета

Чтобы пакет не вытеснял чужие события, в манифесте указываются: число линий (семян с продолжениями), средняя длина линии в решениях, окно. Ориентир на первый год производства: **не больше 3 линий на пакет и не больше 8 решений-продолжений на линию**. Сводный отчёт считает, сколько открытых линий одновременно у среднего героя; если больше 4 в 30–60 лет, новые семена откладываются директором (этап 4) или пакетом.

### 3.4. Принципиально разные продолжения

Ветвление считается настоящим, если ветки дают **разные сцены** (разные `id` или разные `variants` текста), а не один сюжет с разными числами. Метрика пакета: для каждой развилки — доля пар «ветка A / ветка B», у которых множества последующих сцен не пересекаются. Существующий тест `lines.test.ts` («разные первые выборы дают непересекающиеся цепочки») — образец; после этапа 3 его обобщённая форма запускается по манифесту.

## 4. Контроль однообразия

### 4.1. Что повторяется

| Уровень | Пример | Нормально? | Как ловить |
|---|---|---|---|
| Событие | тот же сюжет в двух жизнях | да, если он редкий или вариантный | пересечение жизней (§5.1) |
| Тип ситуации | первая любовь в каждой жизни | да | `group` (этап 1) + разнообразие внутри группы |
| Текст и исход | первая любовь с теми же репликами и тем же концом | **нет** | доля сюжетов группы без вариантов, n-граммы |
| Мотив | чай/чашка в 38 сценах, «смена» в 54, окно/стекло/звёзды в 39 | в меру | отчёт мотивов |
| Структура | «третий ответ — ничего не делать, стресс −1» | **нет** | эвристика по эффектам ответов |
| Концовка | отклик «вы долго молчите» | **нет** | n-граммы концовок `result` |
| Повтор внутри жизни | тот же момент 3 раза за жизнь | в меру | доля повторов (сейчас 45% предложенных моментов) |

### 4.2. Автоматические отчёты (после этапа 3)

1. **Мотивы:** основы слов, встречающиеся в N+ сценах; бюджет мотива на пакет (например, не больше трёх «чашек» на пакет). Первая версия уже в `npm run audit:variety` (`motifs`).
2. **n-граммы:** пары сцен с общей последовательностью из 5+ слов; совпадающие концовки `result` (последние 4 слова).
3. **Шаблоны эффектов:** доля сюжетов, где у последнего ответа только `stress < 0`; доля ответов без цены (только плюсы).
4. **Группы ситуаций:** сколько сюжетов в группе, сколько из них вариантные, вероятность встретить одну и ту же сцену группы в двух жизнях.

### 4.3. Повторы внутри одной жизни

Это важнее, чем повтор между жизнями: игрок замечает его сразу. Моментов с `cooldown` — около половины каталога, и почти половина предложенных за жизнь моментов — повторы уже виденных. Нужны: варианты текста моментов (этап 1), «свежесть» в выборе момента (этап 4) и правило пакета: момент с `cooldown` обязан иметь 2+ варианта текста, если он может выпасть больше двух раз за жизнь.

## 5. Проверка достижимости

### 5.1. Метрики (`npm run audit:variety`)

| Метрика | Что значит | Ориентир для пакета |
|---|---|---|
| `shownPct` | доля жизней, где сюжет показан | обычное событие ≥ 3%, ключевое семя ≥ 15% в своей нише |
| `deliveryPct` | показан / был доступен | продолжение ≥ 95%; обычное — для сравнения пакетов |
| `never` | ни разу не показан | 0 (иначе объяснение в манифесте) |
| `rareUnder2Pct` | показан < 2% жизней | только с пометкой «редкость намеренная» |
| `lostFollowups` | продолжение было доступно, но не пришло | 0 |
| `arcsWithoutOutcome` | линия начата, продолжения нет за 20+ лет | ≤ 10%, кроме линий с тихим исходом |
| пересечение двух жизней | Jaccard сюжетов двух случайных жизней | падает с каждым пакетом; для групп ситуаций — может расти |
| новизна k-й жизни | доля сюжетов, не виденных в k−1 прошлых | цель: ≥ 25% в 3-й жизни, ≥ 10% в 10-й |
| вклад пакета | новых сюжетов на жизнь после добавления пакета | отчёт «до/после» по одним seed |

### 5.2. Порядок проверки нового пакета

1. `npm run content` — форма.
2. `npm run audit:variety -- 200 --json before.json` на `main`, затем то же на ветке пакета; сравнить `delivery.perStorylet` пакета и сводные показатели (решений на жизнь, продолжений, повторы, вытеснение чужих событий более чем на 3 п. п.).
3. Для каждой развилки — тест «ветки расходятся» и тест «продолжение приходит» на искусственном состоянии (образец — `late-life.test.ts`, `economy-narrative-t7.test.ts`).
4. Литературное ревью (§2.3).

### 5.3. Чего боты не скажут

Боты отвечают по хэшу и покупают по стратегиям T8. Они не ищут семью, не избегают тяжёлых тем и не читают тексты. Поэтому достижимость, которую видит бот, — нижняя оценка для целеустремлённого игрока и верхняя для невнимательного. Выводы об интересе — только после плейтеста ([PLAYTEST.md](PLAYTEST.md)).

## 6. Несколько исполнителей

### 6.1. Разделение ролей

| Работа | Исполнитель | Почему |
|---|---|---|
| Технические этапы 1, 2, 4 (язык контента, люди, директор) | Claude Opus | Затрагивают согласованность, сохранения, RNG и все будущие пакеты |
| Этап 3 (валидатор, реестр, отчёты), рутинные тесты | Codex или Claude Sonnet | Чётко специфицируется, мало решений вкуса |
| Пакеты с линиями через десятилетия, семья, потери | Claude (Opus для линий, Sonnet для вариантов) | Важна последовательность характеров |
| Пакеты моментов, бытовые сцены, варианты текста | Codex или Sonnet | Объём, ясные правила |
| Литературное ревью | перекрёстно: пишет один, читает другой | Свой текст не видно |

### 6.2. Как не конфликтовать

- **Одна ветка — один пакет.** Ветки `content/<pack-id>`; пакет не правит файлы чужих пакетов, `src/` и `bundle.json` чужих веток (бандл пересобирается после слияния).
- **Префикс ID** из манифеста; валидатор отклоняет ID без префикса (этап 3). Сегодня дубли уже ловятся, но только при сборке общей ветки.
- **Флаги принадлежат пакету.** Пакет пишет только свои флаги; чтение чужих — через `reads` в манифесте. Межпакетные связи лучше делать через журнал решений (`chose`) — тогда изменение чужого флага не ломает связь.
- **Группы ситуаций и линии регистрируются в манифесте.** Новая группа (например, `first-love`) объявляется один раз, остальные пакеты ссылаются на неё.
- **Изменение формата — только техническим этапом.** Пакет, которому не хватает условия, не добавляет его сам: исполнитель пишет запрос в бэклог (как сейчас требует README).
- **Слияние пакетов по одному**, после каждого — `audit:variety` на `main`, чтобы видеть вытеснение.

### 6.3. Нужен ли отдельный инструмент учёта

**Нет.** Достаточно:

1. манифеста пакета (§1.1);
2. генерируемого отчёта связей `npm run content:graph` (этап 3): какие сюжеты пишут флаг, какие читают, какие линии открыты, что ни к чему не ведёт; Markdown-таблица, а не интерактивный редактор;
3. отчёта `audit:variety`.

Редакторская система (визуальный граф, база, веб-интерфейс) стоит дороже, чем несколько сотен сюжетов, и устаревает при каждом изменении формата. Вернуться к вопросу, если каталог перейдёт 1 500 событий или в проекте появятся авторы без доступа к репозиторию.

## 7. Правила качества (чек-лист пакета)

- [ ] Манифест: префикс, флаги (пишет/читает), линии, группы, возрастные окна.
- [ ] Не меньше половины сюжетов читают прошлое героя (флаг, журнал решений, людей, работу, жильё) — сейчас так у 71 из 137 сюжетов (63 из них — с окном по возрасту события).
- [ ] Каждая развилка: ветки ведут к разным сценам; у каждой ветки отклик или пометка «тихий исход».
- [ ] Каждый человек в тексте гарантирован (`present`/`needs`), учтены смерть и разрыв.
- [ ] Возраст: сцена соответствует возрасту героя **и** возрасту людей (ребёнок, родители 60+).
- [ ] Профессия и рабочий статус: сцена не противоречит пенсии, стажировке, 0,6 ставки.
- [ ] Мотивы в бюджете пакета; нет совпадающих концовок; у каждого ответа есть цена.
- [ ] Треть сюжетов без кризиса; не больше одной потери.
- [ ] `audit:variety` до/после: 0 `never`, 0 `lostFollowups`, вытеснение чужих событий ≤ 3 п. п.
- [ ] Тесты на развилки и окна продолжений.
- [ ] Литературное ревью другим исполнителем.

## 8. Проверка правдоподобия: что автоматизируется

| Ошибка | Автоматически | Как | Где нужна редактура |
|---|---|---|---|
| Несуществующее прошлое («как в тот раз, когда ты…» без события) | частично | текст с отсылкой обязан иметь `requires` на флаг/решение; эвристика по словам «тогда», «в тот раз», «помнишь» без условия на прошлое | смысловые отсылки без ключевых слов |
| Умерший персонаж | да | метка → `present`; движок и валидатор используют один список людей (сейчас `sibling` не охраняется движком — аудит §5) | упоминание без метки («твоя мать») |
| Возраст | да | окна героя, `personAge` для детей и родителей; инвариант «ребёнок с детской сценой не старше max» | «ты ещё слишком молод» в сцене 45+ |
| Профессия и рабочий статус | да | `job`, `work`, `regime`; тест: профессиональные сцены не приходят на пенсии без явного разрешения | «на смене» у пенсионера в тексте без условий |
| Игнор прошлых решений | частично | отчёт: сюжеты, которые ставят флаг, противоречащий уже стоящему (`friendState: close` при `estranged`) | эмоциональная несовместимость |
| Обещанное продолжение не приходит | да | `lostFollowups`, `arcsWithoutOutcome`, окна `since/until` ≥ 3 лет | — |
| Дублирует существующую линию | частично | `group` ситуаций; n-граммы тел; одинаковые наборы флагов в `requires` | одна и та же драма в другой одежде |
| Опечатка в значении флага | да (после этапа 3) | значения из манифеста; сейчас валидатор проверяет только имя флага | — |
